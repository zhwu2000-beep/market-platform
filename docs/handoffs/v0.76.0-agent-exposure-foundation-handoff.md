# v0.76.0 Agent Exposure Foundation handoff

## Release-readiness outcome

The v0.76.0 implementation is narrow, deterministic, and free of the
forbidden integrations reviewed below. Policy provenance, capability schema
metadata, and ADR wording have been hardened for the final release candidate.
Its focused tests and all project quality gates pass. No release blockers
remain.

This release establishes only the in-process Agent Exposure Foundation. It
does not introduce an LLM runtime, remote Agent API, MCP integration, HTTP
transport, or autonomous behavior. Future transport and external Agent
integration remain separately scoped.

## Reviewed scope

The v0.76.0 candidate consists of:

- the ADR 0033 status change from proposed to accepted for the Agent Exposure
  Foundation;
- `market_platform.agent_exposure` capability metadata and explicit allow-list;
- the capability-specific Daily Technical Strategy exposure facade;
- the bounded Daily Technical Strategy Agent response projection with policy
  provenance metadata;
- explicit application request, application response, and Agent projection
  schema discovery metadata; and
- focused unit coverage for capability metadata, delegation, projection, and
  dependency restrictions.

The release does not change the v0.75 application request, application
response, service orchestration, domain policies, or financial semantics.

## Capability descriptor boundary

`AgentCapabilityDescriptor` is frozen, slotted, and metadata-only. It retains
exactly a versioned capability ID, display metadata, the associated application
request and response schema versions, the Agent response projection schema
version, fixed read-only status, and its own fixed descriptor schema version.

The descriptor has no callable execution or transport hook. Construction of
another descriptor does not expose it: the immutable allow-list contains only
`daily_technical_intelligence/v1`, and membership requires the exact allow-listed
string ID. Existing historical replay and trading-signal application services
are not included.

The descriptor deliberately distinguishes the underlying v0.75 application
request and response contracts from the separately versioned bounded Agent
response projection. Each schema has its own explicit descriptor field; no
existing application schema field is repurposed.

## Facade dependency direction

The dependency direction is:

```text
DailyTechnicalStrategyAgentExposureFacade
    -> DailyTechnicalStrategyApplicationService
        -> released application orchestration
            -> released domain boundaries
```

The facade receives the application service by dependency injection, accepts
the exact application request type, delegates once to the service's async
operation, and constructs the bounded projection from the completed application
response. Application and projection exceptions propagate unchanged.

The facade imports no research runner, domain policy, provider, trading path,
or generic application executor. It performs no validation, canonicalization,
policy selection, financial calculation, stage orchestration, retry, fallback,
or result reinterpretation.

## Projection contract

`DailyTechnicalStrategyAgentResponseProjection` is factory-created, frozen,
slotted, and versioned as
`daily_technical_strategy_agent_response_projection/v1`. It requires an exact
valid `DailyTechnicalStrategyApplicationResponse` and creates a detached flat
projection.

The projection retains:

- the application request fingerprint;
- canonical instrument ID and requested trading identity;
- UTC analysis time;
- technical-analysis and instrument-integrity source fingerprints;
- Interpretation, Assessment, and Strategy fingerprints;
- the policy ID, behavioral revision, and identity fingerprint for
  Interpretation, Assessment, and Strategy;
- source quality and warnings;
- the four descriptive Interpretation states;
- Assessment outcome and finding codes; and
- descriptive Strategy mode and rule code.

It does not retain the verified-research graph, domain objects, comparison
evidence, registry state, raw market data, or a complete application response.
Policy provenance is retained only as bounded scalar metadata: the projection
does not expose `TechnicalPolicyIdentity` objects, configurations, or policy
implementations. It adds no response, aggregate, exposure, or other
fingerprint family and has no dictionary or transport codec.

The projection preserves the fingerprint links and policy profile metadata
needed to relate its flattened values to the authoritative application result.

## ADR 0033 compliance

The implemented dependency and authority boundaries comply with ADR 0033 in
the following material respects:

- exposure is capability-specific and allow-listed rather than reflective or
  generic;
- the exposure layer delegates to the public application service and does not
  call domain runners or policies;
- the application and domain layers remain the sole owners of orchestration,
  correspondence, and financial semantics;
- the result remains descriptive intelligence and is not translated into a
  trading action;
- the projection is explicit, versioned, bounded, and provenance-bearing;
- the operation introduces no hidden clock, fallback, policy choice, Agent
  memory, or cross-capability synthesis; and
- the exposure surface remains read-only with respect to trading authority.

ADR 0033 is accepted for the v0.76 Agent Exposure Foundation and now reflects
the implemented metadata, facade, and bounded projection. Its acceptance does
not introduce an LLM runtime, remote Agent API, MCP, HTTP transport, or
autonomous behavior. Future transport and external Agent integration require
separate scope and architectural approval.

## Forbidden integrations absence

The v0.76.0 production package imports only its own exposure modules, the
Daily Technical Strategy application contracts and service, and Python
standard-library modules. Static import review and focused architecture tests
found no dependency on:

- an Agent or conversational runtime;
- AI model or prompt code;
- CLI surfaces;
- MCP or another tool protocol;
- HTTP, remote API, serialization, or transport adapters;
- TradingView visualization or webhook ingress;
- providers or market-data acquisition;
- the legacy `market_platform.strategy.Strategy` family;
- the parallel research workflow;
- Trade Planning, Risk, Execution, broker mapping, or order submission; or
- persistence, memory, user profiles, retries, or side effects.

The existing application and domain packages do not import
`market_platform.agent_exposure`; the dependency remains outward from exposure
to application.

## Future direction

Treat v0.76 as a single-capability exposure foundation and keep the v0.75
application boundary and Daily Technical domain semantics frozen unless a
defect is found.

Future work may address remote Agent transport, authentication and
authorization, external acquisition boundaries, and operational Agent
integration. Each requires separate scope and must preserve the accepted ADR
0033 dependency, semantic-authority, and allow-list boundaries.

Do not broaden a future release automatically to another intelligence family
or to a generic executor. Any subsequent capability must have its own released
domain and application boundary, explicit allow-list entry, and bounded
projection.

## Remaining concerns

No v0.76.0 release blockers remain. Remaining concerns are future scope only:

- remote Agent transport;
- authentication and authorization;
- external acquisition boundaries; and
- operational Agent integration.
