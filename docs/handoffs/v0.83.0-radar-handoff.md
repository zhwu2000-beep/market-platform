## 4. Delivered production capabilities

The delivered flow is bounded to observation and selection:

```text
explicit caller Profile + canonical instrument + evaluation as_of
→ lazy calendar / fresh completed-daily facts
→ ordered Trigger / configured EMA relation evaluation
→ actual Pipeline outcome
→ eligible MeaningfulChange comparison and coordinated observation commit
→ passive single-symbol / sequential batch response
→ STOP
```

Eligibility is application-owned; not every Pipeline result advances state.

| Area | Implementation and boundary |
| --- | --- |
| Calendar | `radar/calendar.py`: eight session operations, owned errors, UTC public times, exact actual-close inclusion, early closes, DST and coverage. `exchange-calendars==4.13.2` is behind the adapter; XNYS remains private. |
| Identities and resolution | `radar/core.py`, `radar/resolver.py`: deeply immutable passive Gate/Profile configuration, ordered fingerprints, unique occurrence IDs and code-owned allow-listed factories. |
| Lazy execution | `radar/context.py`, `radar/pipeline.py`: execution-local typed facts and retained ordinary failures; exact Profile order, short-circuiting and actual executed-prefix results. |
| Trigger and legacy checkpoint | `radar/trigger.py`, `radar/observation.py`: completed-session/content comparison, bounded reasons, versioned market-content scope and legacy checkpoint correspondence. |
| Storage and advancement | `radar/checkpoint_store.py`, `radar/application.py`: strict lookup, filesystem publication and application-owned advancement after qualifying evaluation. |
| Current content | `radar/current_content.py`: one fresh bounded Polygon acquisition when needed; exact 250-session coverage, metadata/OHLCV/mapping validation and shared normalized history. No cache fallback. |
| EMA observation and Gate | `radar/lightweight_observation.py`, `radar/ema_relation.py`: shared EMA8/EMA20 relation fact; explicit Profile-configured accepted relations; observation mathematics independent of selection. |
| MeaningfulChange | `radar/meaningful_change.py`: pure baseline, incompatibility, unchanged and transition decisions retaining prior/current correspondence. |
| Coordinated state | `radar/observation_state.py`: market observation, lightweight observation and committed decision with actual Profile/outcome correspondence. |
| Production composition | `application/radar_single_symbol.py`: trusted mapping, calendar, provider behind an injected HTTP client, lazy configuration validation, fact bindings, state store and owned-client cleanup. |
| Sequential batch | `application/radar_batch.py`: caller order, normalized unique symbols, common Profile/as_of, per-symbol ordinary-failure isolation and retained completed results. |

Paths in the table are relative to `src/market_platform/`. Public entrypoints
are `run_single_symbol_radar` and `run_radar_batch` in their respective modules;
no package-root re-export or CLI is promised.

Application advancement remembers valid SELECTED observations and valid
downstream FILTERED observations after a qualifying Trigger PASS. ATTENTION,
FAILED and earlier filtering without that PASS do not advance. Missing or
incoherent required observations fail preparation rather than commit partial
state. Legacy bootstrap and complete-state Level-0 behavior are described below.

Single-symbol and batch projections expose passive identities, actual Pipeline
results, advancement and corresponding saved state/decision. They do not expose
live exception text or synthesize Candidate/research outputs. Preparation and
save failures preserve the completed Pipeline; unrelated batch instruments
continue without rolling back earlier completed instruments.

## 5. Frozen contract surface

These implementation contracts are frozen for the v0.83.0 release.

### Execution and identity

| Contract | Semantics |
| --- | --- |
| Gate dispositions | `PASS` continues; `DROP` and `ATTENTION` terminate. Unexpected exceptions are execution failures. |
| Pipeline outcomes | `SELECTED`: all configured Gates passed; `FILTERED`: a Gate dropped; `ATTENTION`: expected operational/data condition; `FAILED`: unexpected execution failure. |
| Executed prefix | Only actual returned Gate results, in Profile order; the failing occurrence is recorded without a synthetic disposition. |
| Gate identity | `radar_gate_identity/v1`; definition ID, behavioral revision, configuration schema/content and deterministic fingerprint. |
| Profile identity | `radar_profile/v1`; exact ordered occurrences and immutable configuration determine the fingerprint. |
| Observation correspondence | Profile selection does not redefine mathematical EMA identity; saved state retains the actual Profile fingerprint and Pipeline outcome. |

### Trigger reasons

The Trigger key is `session_content_trigger / 1 / session_content_trigger/v1`
with empty configuration.

| Disposition | Reasons |
| --- | --- |
| PASS | `BASELINE_REQUIRED`, `NEW_COMPLETED_SESSION`, `MARKET_CONTENT_CHANGED` |
| DROP | `UNCHANGED` |
| ATTENTION | `PRIOR_STATE_UNAVAILABLE`, `PRIOR_INSTRUMENT_MISMATCH`, `PRIOR_NOT_SESSION`, `PRIOR_SESSION_AHEAD`, `CURRENT_CONTENT_UNAVAILABLE`, `CURRENT_INSTRUMENT_MISMATCH`, `CURRENT_SESSION_MISMATCH`, `INCOMPARABLE_CONTENT_SCOPE` |

### Observation and policy schemas

| Schema | Meaning |
| --- | --- |
| `radar_market_content_scope/v1` | Bounded completed-daily, split-adjusted, non-dividend-adjusted OHLCV history scope with midnight-UTC session labels. |
| `radar_observation_checkpoint/v1` | Instrument, completed session, normalized content identity, acceptance time and scope. |
| `radar_ema8_ema20_observation/v1` | Instrument, observation definition/revision/schema, session, content identity/scope, relation and UTC evaluation as_of. |
| `radar_meaningful_change_decision/v1` | Prior/current observations, applied policy, classification, reason and bounded comparison/incompatibility provenance. |
| `radar_observation_state/v1` | Corresponding market observation, lightweight observation, committed decision, Profile fingerprint and Pipeline outcome. |

EMA observation definition is `ema8_ema20_relation_observation`, calculation
revision `1`, with states `ABOVE`, `EQUAL`, `BELOW`. It uses the existing
`calculate_ema` semantics for periods 8 and 20 and exact latest-value comparison.
The Gate key is `ema8_ema20_relation / 1 / ema8_ema20_relation/v1`; its explicit
`accepted_relations` configuration does not alter observation identity.

MeaningfulChange policy is `ema8_ema20_relation_transition`, behavioral revision
`1`. Gate behavioral revision, observation calculation revision and comparison
policy revision are separate identities.

| Classification | Reason / behavior |
| --- | --- |
| `BASELINE_INITIALIZED` | Missing prior; no meaningful change or invented history. |
| `INCOMPARABLE_BASELINE_INITIALIZED` | Valid incompatible definition/revision/schema; bounded provenance, no transition. |
| `STATE_UNCHANGED` | Comparable unchanged relation, including new sessions or corrected content; no meaningful change. |
| `STATE_TRANSITION` | `NEW_SESSION_STATE_TRANSITION` or `CORRECTED_CONTENT_STATE_TRANSITION`; all six changed relation pairs are meaningful under revision 1. |

Same-session corrections require equal concrete scope and changed normalized
content. Identical same-session content/calculation with a different relation
is incoherent. Wrong instrument, reversed session order and corrupt/unavailable
state cannot masquerade as baseline migration.

### Lookup, advancement and failure envelopes

- State lookup: `ABSENT`, `UNAVAILABLE`, `LEGACY_CONTENT_ONLY`,
  `PRESENT_COMPLETE_STATE`. Legacy market-only lookup retains `PRESENT`,
  `ABSENT`, `UNAVAILABLE`; malformed state raises rather than becoming absence.
- Current content/history/lightweight lookup: `PRESENT` or `UNAVAILABLE`.
- Advancement: `SAVED` requires corresponding checkpoint, decision and complete
  state; `NOT_ADVANCED` has none of those current-execution payloads.
- Pipeline failures: `GATE_EXCEPTION`, `IDENTITY_MISMATCH`, `INVALID_RESULT`.
- Batch failures: `EXECUTION_ERROR`, `CHECKPOINT_SAVE_FAILED`,
  `OBSERVATION_PREPARATION_FAILED`. The latter two retain the actual completed
  Pipeline. A normal response containing Pipeline `FAILED` remains distinct
  from a batch wrapper failure.

## 6. Coordinated persistence and legacy behavior

The Application performs one retained semantic prior lookup per evaluation when
needed. Both the Trigger's market-checkpoint projection and MeaningfulChange
comparison use that retained semantic prior. `save_state()` separately performs
a fail-closed publication preflight; this is not a second semantic comparison
lookup or a concurrent-writer protocol.

One coordinated record publishes market observation, lightweight observation and
committed decision together. Return-value correspondence is validated before
publication. The process-visible commit point is `os.replace`, after writing,
flushing, file-fsync and closing the temporary file. Pre-publication failures
preserve the prior authoritative bytes and permit retry. The committed decision
retains the bounded prior/current comparison basis after publication; orphan
temporary files have no authority.

There is **no directory-fsync or universal power-loss durability guarantee**,
and no CAS, locking or stale-writer protection. One owner must prevent
overlapping evaluations/writes for the same instrument. Distinct instruments
have no shared transaction.

Valid legacy content-only checkpoints remain readable and explicitly identified.
Legacy `UNCHANGED` may bootstrap technical state after the actual Pipeline has
terminated as FILTERED. The Application calculates a real current observation
from the retained fresh history, records `BASELINE_INITIALIZED`, and commits the
combined state. It neither synthetically executes the skipped EMA Gate nor
infers a historical relation/transition. Complete state cannot be downgraded
through the legacy save API.

Complete-state Level-0 `UNCHANGED` remains `NOT_ADVANCED`: no state rewrite,
new comparison decision or downstream observation calculation is required.
With Trigger before EMA, the EMA Gate/fact remains skipped. Caller Gate order
is preserved; facts requested before the Trigger may already have run.
Current-content acquisition still refreshes the bounded window under ADR0048;
Level 0 is not a cache-only or no-I/O guarantee.

## 14. Known bounded limitations

- Regular-session completed daily only; NASDAQ-facing calendar semantics and
  Polygon as the current production acquisition path.
- Fixed 250-session history; no correction detection outside that retained
  acquisition window. Instruments lacking required coverage are unavailable.
- EMA8/EMA20 relation is the only current lightweight technical observation;
  unchanged relation does not detect every numeric movement or intermediate
  state transition between evaluations.
- No global cache fallback: current-content evaluation requires fresh bounded
  acquisition, shared only within that execution.
- Single-owner checkpoint writer assumption; no overlapping same-instrument
  execution, CAS or stale-writer protection.
- No directory-fsync or universal power-loss guarantee.
- No exactly-once Candidate delivery because Candidate does not exist.
- Sequential batch only; no cross-instrument transaction. The synchronous
  composition requires a thread without an already-running asyncio event loop.

These are current contract boundaries, not claims of defects or commitments to
broaden the release scope.
