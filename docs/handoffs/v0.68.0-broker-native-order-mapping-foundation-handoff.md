## Mapper boundary

The runtime-checkable protocol declares exact execution-target, mapper,
version, policy-fingerprint, and instrument-namespace metadata plus one
keyword-only mapping operation. Protocol checking proves structural member
availability only. After every domain precondition passes, the evaluator reads
each metadata property exactly once in declared order, validates the immutable
local snapshots, binds `map_order` once, invokes it once, and never rereads
metadata.

`mapper_version` is explicit visible-ASCII protocol metadata rather than a
module, class, function, file, installation, or object identity. Mapper ID,
version, and policy fingerprint bind declared translation provenance; they do
not prove mapper authenticity or correctness.

Side, order-type, TIF, and session tokens are exact bounded visible-ASCII
adapter vocabulary. Their interpretation is a mapper-conformance responsibility.
The platform does not impose BUY, SELL, MARKET, LIMIT, DAY, or session-token
spellings and does not claim that shape-valid opaque tokens are semantically
correct or broker-accepted.

## Representation and correspondence

`BrokerNativeOrderRepresentation` owns one independently reconstructed
`ExternalInstrumentIdentity`, opaque tokens, exact canonical quantity,
conditional canonical limit price/currency, schema, and fingerprint. Quantity
reuses the instruction delta-result bounds; price and currency reuse
`LimitPriceChoice` canonical rules. Decimal scale is non-semantic, so `1`,
`1.0`, and `1.00` retain and project as `1`. Retained noncanonical Decimal state
fails even with a recomputed fingerprint.

`map_broker_native_order` requires exact validated specification, capability
profile, compatible structural result, and caller-supplied `InstrumentMapping`.
It verifies source fingerprints, canonical instrument identity, half-open
mapping applicability at `instruction.plan_as_of`, mapper target, and external
namespace before mapper invocation. It reconstructs a fresh external identity
for the mapper. No mapping lookup, search, reverse resolver, ambiguity choice,
route selection, or live contract lookup exists.

Returned output must be an exact fully valid representation. The platform
independently verifies external identity, canonical quantity, MARKET price
absence, and LIMIT numeric price/currency correspondence. It shape-validates
opaque tokens without falsely interpreting them.

## Mapping value and threat boundary

`BrokerNativeOrderMapping` contains mapper provenance, four exact source
fingerprints, and complete owned `native_order` semantic state. It retains no
specification, capability profile, compatibility result, instrument mapping, or
mapper instance. Parent validation independently validates the child and
requires parent namespace to equal the child's external namespace. Permanent
regressions prove this invariant survives refingerprinting of either side.

Representation and mapping are self-contained canonical value artifacts. They
validate current exact types, Decimal canonicality, nested state, schemas,
semantic invariants, and fingerprints. Fingerprints bind current values, not
factory provenance, mapper code identity, authenticity, or correctness. A
coherent rewrite into another completely valid artifact remains outside
construction-origin authenticity. No registry, attestation, weak reference,
retained upstream evidence, or process-local owner identity was introduced.

## Errors and scope

Malformed public inputs, ineligible preconditions, cross-source contradictions,
inactive mappings, metadata mismatches, and malformed mapper output raise
`ExecutionPlanningValidationError`. Corrupted retained sources or results and
internal parent/child contradictions raise
`ExecutionPlanningCorrespondenceError`. Direct construction raises `TypeError`.
Unrelated mapper property or operation exceptions propagate unchanged.

Mapping is pure, offline, and precedes authorization so a future authority can
bind the exact mapped artifact. It is not an SDK object or call, authorization,
risk approval, routing approval, submission request, broker acceptance,
acknowledgement, execution, or lifecycle state. It adds no credential, account,
balance, buying power, network, retry, persistence, configuration, environment
loading, live discovery, market/calendar decision, routing optimization,
rounding, lot, fractional-share, tick, collar, band, or token-semantic logic.
