## 8. Long-Term System Architecture

The long-term architecture has five conceptual layers. Governed Research is released; the other layers below are architecture direction, not claims of implemented workflows.

### 1. Radar

Question:

> Which instruments deserve deeper research?

Radar is:

- wide;

- shallow;

- low-cost;

- non-authoritative;

- multi-symbol;

- configurable;

- intended for continuous scanning.

### 2. Governed Research

Question:

> What do we reliably know about this instrument now?

This is largely the system already built through v0.82:

```text
Evidence
→ Qualification
→ Bridge
→ Technical
→ Interpretation
→ Assessment
→ Strategy
```

### 3. Scenario / Risk / Plan

Expected major focus after Radar.

Question:

> If action becomes appropriate, what are the scenarios, conditions, invalidation rules and risk plan?

Likely concepts include:

- bullish/base/bearish scenarios;

- trigger conditions;

- invalidation;

- time horizon;

- relevant price zones;

- risk/reward context;

- potential entry zone;

- target zone;

- stop/invalidation concept;

- risk budget;

- position constraints.

This layer produces a plan, not execution authority.

### 4. Execution & Runtime Supervision

Question:

> Is this action authorized now, and does execution remain compliant with the approved plan?

Likely responsibilities:

- execution contract;

- signal / order intent;

- risk approval;

- execution authorization;

- runtime supervision;

- stop discipline;

- position/risk limits;

- prevention of unauthorized averaging down;

- prevention of stop widening;

- prevention of thesis substitution.

### 5. Shadow Observer

Question:

> Did the decision process remain internally consistent and disciplined?

Shadow Observer is a planned independent, temporal-blind process-audit / black-box layer.

It is NOT a hindsight optimizer.

It evaluates historical decisions using only information actually available at the decision time.

It should identify:

- incomplete observation;

- missing evidence;

- inconsistent reasoning;

- unjustified assumptions;

- discipline violations;

- thesis substitution;

- stop widening;

- unplanned averaging down;

- process drift.

Later outcomes may calibrate aggregate process performance but must not rewrite historical decisions.

## 10. Radar Internal Model

Three core concepts are planned. Their contracts, result vocabulary and examples below are PROVISIONAL, not frozen implementation details:

### RadarGate

One bounded filtering/observation operation.

Examples:

```text
SessionGate
MACDCrossGate
RSIZoneGate
ATRExpansionGate
VolumeExpansionGate
PriceStructureGate
```

A Gate should support a simple contract conceptually similar to:

```text
input
→ evaluate
→ PASS / DROP / ATTENTION
```

### RadarProfile

A named/versioned configuration selecting:

- which Gates are active;

- their order;

- parameters;

- applicable context.

Example:

```text
trend_radar_v1
Session
→ MACD
→ RSI
→ ATR
```

Another Profile may instead use:

```text
reversal_radar_v1
Session
→ RSI
→ momentum reversal
→ volume
→ structure
```

Profiles may eventually vary by:

- asset class;

- sector;

- volatility regime;

- market regime;

- strategy/playbook.

Profile selection must remain explicit and auditable.

Radar must not silently rewrite its own strategy.

### RadarPipeline

The execution sequence produced by a RadarProfile.

Example:

```text
Gate 0
→ Gate 1
→ Gate 2
→ Gate 3
→ Radar Candidate
```

Pipeline design should support coarse-to-fine filtering.

General principle:

> Cheap, high-selectivity gates belong earlier.

Expensive gates should operate only on survivors.

Future optimization may consider:

```text
cost × selectivity
```

but v0.83 should not initially self-reorder gates.

## 11. Radar Change Semantics

The provisional change model is below. MeaningfulChangePolicy is not finalized; these examples neither freeze a contract nor grant automatic escalation authority:

### LEVEL 0 — NO CHANGE

No new completed session and no normalized market-content change.

Action:

```text
do nothing
```

### LEVEL 1 — OBSERVED CHANGE

A new completed session exists, but no material lightweight state transition occurred.

Action:

```text
update lightweight observation
do not run full Governed Research
```

### LEVEL 2 — MATERIAL CHANGE

A meaningful market-state change occurred.

Action:

```text
produce Radar / Monitoring Candidate
request full Governed Research
```

Possible reasons include:

- historical data correction;

- lightweight classification/state transition;

- material numeric movement.

Exact `material_numeric_movement` semantics are not yet frozen.

### Baseline Required

A newly added instrument may require an initial full governed evaluation because no prior baseline exists.

This is an orchestration trigger, not market materiality.

### Attention

Data problems should not be interpreted as investment opportunities.

Examples:

```text
data_unavailable
data_stale
observation_incomplete
```

These belong to an attention/operational channel rather than Radar Candidate semantics.

## 12. Important Radar Negative Rules

The following changes must NOT by themselves be interpreted as material market changes:

- Evidence fingerprint changed;

- artifact fingerprint/version changed;

- execution ID changed;

- history sequence changed;

- provider request ID changed;

- receipt timestamp changed;

- `query_as_of` changed;

- cache file changed.

These can vary even when market content has not materially changed.

The existing Evidence material fingerprint mixes market content with provenance/request/time context and therefore is unsuitable as a standalone Radar materiality signal.

`HistoricalPriceSeries.content_fingerprint` is a better exact normalized market-content comparison primitive because it covers normalized symbol, timestamps and OHLCV rows.

However:

> exact content difference != meaningful change.

Meaningful change remains a market-platform-owned policy decision.

## 13. Exchange Calendar / Radar Gate 0 — ADR0046

**FROZEN / COMPLETED:** Exchange Calendar Adoption Spike and build-versus-reuse
selection. The isolated Python 3.14.6 spike passed 573 TEMP-only assertions.

[ADR0046 — Radar Exchange Session Calendar Foundation](../adr/0046_radar_exchange_session_calendar_foundation.md)
is **Accepted**, committed as:

`944865b9732af3fd7f4624c1f08a993249abf178`

Frozen initial backend: **exchange-calendars == 4.13.2**, behind a
market-platform-owned adapter. Public venue remains **NASDAQ**; the
**NASDAQ -> XNYS** calendar mapping is private implementation detail.
`XNYS` must not become instrument/operator identity or leak into public domain
results. Replacing the backend must preserve `NASDAQ` identity.

Both NASDAQ and XNAS aliases in the tested backend resolve to
`XNYSExchangeCalendar`, named `XNYS`. This bounded mapping passed the approved
2026 Nasdaq regular-session references: all ten supplied closed dates, both
13:00 ET early closes (November 27 and December 24), and nearby normal sessions.
The tested 2026 schedule had 251 sessions and exactly those two early closes.
This does NOT mean Nasdaq and NYSE are universally identical or prove all
historical/future exceptional closures.

The frozen conceptual public contract is `ExchangeSessionCalendar`:

```text
is_session(session_date: date) -> bool
session_open(session_date: date) -> aware datetime
session_close(session_date: date) -> aware datetime
is_early_close(session_date: date) -> bool
previous_session(session_date: date) -> date
next_session(session_date: date) -> date
latest_completed_session(as_of: aware datetime) -> date
sessions_in_range(start: date, end: date) -> tuple[date, ...]
```

Frozen semantics:

- Standard-library public date/datetime values; pandas/library types stay private.
- Session open/close return aware UTC datetime values.
- Previous/next mean STRICTLY before/after the supplied calendar date, including
  session, weekend and holiday inputs; never return the input date itself.
- Latest completed session uses actual `session_close <= as_of`: the exact close
  instant is included. Early-close completion occurs at the actual early close,
  not the normal 16:00 ET close.
- `is_early_close` supplies the fact without caller hard-coded close comparisons.
- DST comes from timezone/calendar behavior, not fixed UTC offsets.
- Coverage is explicit; unsupported queries fail through owned calendar errors.
  Non-session open/close/early-close queries also fail, without date substitution.
- Backend exceptions remain contained; naive as-of timestamps and reversed ranges
  are rejected. Session ranges are ordered inclusive tuples of session dates.
- **Session completed != provider bar available.** Polygon or another provider
  may not yet have published/delivered the completed daily bar.

Calendar is non-authoritative Radar infrastructure. It must NOT by itself create
Evidence, establish governed Freshness, create a Radar Candidate, determine
MeaningfulChange, invoke Governed Research, or create investment/execution
authority. ADR0046's full authority exclusions remain controlling.

Future Gate 0 can compare `last_observed_session` with
`latest_completed_session(as_of)` to ask whether a newer expected regular session
exists. Calendar supplies only that session fact; observation, materiality and
escalation remain separate later contracts.

`pandas-market-calendars == 5.4.0` also passed the bounded checks. It was not
selected because it depends on exchange-calendars and added a package/API layer
without demonstrated semantic advantage for this contract; it is not defective.

No production Calendar code or permanent dependency has been added. The backend
selection is approved, but later implementation must validate resolution against
the actual project environment and lockfile before dependency adoption is
committed. ADR0046 freezes semantics, not a concrete Python module location or a
broader Radar framework.

## 14. Open-Source Reuse Policy

market-platform should not unnecessarily reimplement mature infrastructure.

Default policy:

```text
1. Borrow proven ideas/designs
2. Prefer our own contract
3. Wrap third-party implementation behind adapter
4. Use direct dependency where appropriate
5. Extend/subclass if needed
6. Fork/vendor only as a last resort
```

General architecture:

```text
market-platform contract / semantics
            ↓
     market-platform adapter
            ↓
 third-party implementation
```

Avoid:

```text
third-party framework
        ↓
market-platform architecture forced around it
```

Generic infrastructure may be borrowed:

- exchange calendars;

- scheduling;

- statistical algorithms;

- execution adapters;

- backtesting infrastructure.

market-platform must retain ownership of:

- Radar semantics;

- MeaningfulChangePolicy;

- Evidence/governance;

- Scenario/Risk/Plan;

- execution authority;

- risk constraints;

- Strategy/Playbook approval;

- Shadow Observer semantics.

Before adopting a library, evaluate:

```text
Capability fit
License fit
Architecture fit
Authority fit
Maintenance fit
Build-vs-reuse
```

Prefer wrapping over forking.

## 17. Strategy Validation Ladder

The default strategy-validation approach should remain as simple as necessary.

### Level 1 — Signal Study

Cheap statistical screening.

Example:

```text
Rule
↓
scan large historical universe
↓
signal occurrences
↓
forward-return distributions
```

Possible outputs:

- count;

- 1/5/10/20-day forward return;

- win rate;

- mean;

- median;

- regime/sector breakdown.

This is intended to rapidly reject weak ideas.

### Level 2 — Portfolio Backtest

Only promising strategies proceed to portfolio simulation.

Potential concerns:

- initial capital;

- position sizing;

- commissions;

- slippage;

- holding rules;

- portfolio constraints;

- turnover;

- benchmark.

Outputs may include:

- CAGR;

- max drawdown;

- Sharpe;

- Sortino;

- exposure;

- turnover;

- win/loss;

- regime breakdown.

Mature external backtesting and execution engines should be evaluated before market-platform builds generic simulation infrastructure itself.

Potential reference/adoption candidates include:

- NautilusTrader;

- QuantConnect LEAN;

- other mature event-driven engines.

### Level 3 — Historical Decision Replay

Only required for strategies whose behavior genuinely depends on contextual Agent reasoning, such as:

- news interpretation;

- financial-report reading;

- multi-source synthesis;

- discretionary price-action interpretation;

- dynamically selected Playbooks.

This mode would enforce point-in-time information boundaries and simulate the Agent moving through history.

It is an optional advanced validation mode where contextual Agent reasoning requires it, not a mandatory level for ordinary deterministic strategies.

## 18. Point-in-Time Correctness

Any future backtest/replay system must prevent look-ahead bias.

The relevant question is not merely:

```text
What was the price on date X?
```

but:

```text
What information was actually available to the system as of date X?
```

Existing market-platform concepts such as:

- `as_of`;

- `available_at`;

- effective times;

- history;

- exact occurrence identity;

- provenance;

are therefore valuable foundations for future Strategy validation and Shadow Observer work.

Computer-use Agents should be treated as Executors, not autonomous sources of investment authority.

prefer:

- existing Agent capability;

- plugin/tool;

- MCP/tool integration;

- computer-use;

If the feature represents:

- investment semantics;

- authority;

- Playbook;

- process discipline;

- audit;

it remains valuable to own internally even as models improve.
