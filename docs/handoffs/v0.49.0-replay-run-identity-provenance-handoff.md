# v0.49.0 Replay Run Identity and Provenance Handoff

## Release Status

Implementation is complete on `feature/v0.49.0-replay-run-provenance` and remains
uncommitted and unreleased. Required validation is complete. Package version remains
`0.1.0`.

## Scope

v0.49.0 adds an opt-in, deterministic in-memory identity boundary around the
unchanged historical Replay result:

- versioned fingerprinting for normalized replay specifications;
- provider-independent content identity for retained canonical historical prices;
- signal, structure, state-model, ordered strategy, and software identities;
- immutable requested and actual run provenance;
- a deterministic input/resolution-based run fingerprint;
- additive `HistoricalReplayService.run_execution()`.

## Fingerprint Families

All new identities use compact UTF-8 JSON, sorted keys, finite canonical values,
an explicit family schema version, SHA-256, and `sha256:<hex>` output.

- specification: normalized symbol, interval, and requested UTC context/evaluation
  bounds;
- dataset content: canonical symbol and every retained timestamp/OHLCV row in
  canonical order, excluding provider and interval;
- run: specification and dataset fingerprints, actual provider, actual context and
  evaluation bounds/counts, derivation identities, state model, ordered strategies,
  and caller-supplied software revision/dirty state.

Existing observation, strategy configuration, research, and benchmark fingerprint
implementations are unchanged.

## Default and Custom Derivations

Replay has no custom signal-service injection boundary, so the built-in signal
identity is resolved from the actual default constants. The default structure
identity is resolved from `PriceStructureConfig` and its versioned methodology.
Custom structure services must receive an explicit
`ReplayStructureDerivationIdentity` for `run_execution()`; legacy methods continue
to accept them without identity.

State-model ID/version are required. A state-model configuration fingerprint is an
optional caller-supplied fact because the existing protocol does not expose one.
Software revision is required and caller supplied; no Git command executes inside
Replay or data models.

## Compatibility Guarantees

- `run()` and `run_with_specification()` retain signatures and result types.
- `HistoricalReplayResult`, step, summary, table, JSON, and CSV schemas are
  unchanged.
- `execution.result.to_dict()` is exactly equal to the existing specification path
  for identical inputs.
- Context/evaluation semantics, empty-range errors, future isolation, canonical
  normalization, and custom prefix isolation remain unchanged.
- Existing benchmark result fingerprints remain unchanged.

## Reproducibility Limits

Run identity verifies declared inputs and resolved facts; it does not store or
recover data. Provider revisions, adjusted-price/corporate-action semantics,
exchange calendars, entitlements, dependency environments, and arbitrary custom
component code remain outside the provenance payload.

## Explicit Non-Goals

Persistence, Replay repositories, manifests/artifacts, CLI provenance output,
result-schema changes, cache/dataset registries, fingerprint-family migration,
Git or callable introspection, environment capture, research migration, portfolio,
risk, execution, microservices, event buses, and package-version changes.
