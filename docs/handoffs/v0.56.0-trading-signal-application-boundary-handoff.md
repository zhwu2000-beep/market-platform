# v0.56.0 Trading Signal Application Boundary Handoff

## Status

The implementation is on
`feature/v0.56.0-trading-signal-application-boundary`, remains uncommitted, and
is not yet released. Package version remains `0.1.0`.

## Schemas and Public API

The four schemas are:

- `trading_signal_application_request/v1`;
- `trading_signal_application_response/v1`;
- `order_intent_application_request/v1`;
- `order_intent_application_response/v1`.

`market_platform.application` exports immutable nested source, instrument,
target, and signal inputs; signal and intent requests; strict decoders;
factory-only responses; two explicit services; and narrow trading application
errors. There is no combined facade, nested schema/fingerprint, or response
fingerprint.

## Request Contract

Both requests contain a complete normalized `signal` object with source ID,
source version, optional configuration fingerprint, source event ID, separate
symbol and venue, optional timeframe, long/flat/short target, exact units, and
generated/valid/expiry times. The intent request additionally requires
`decision_as_of`. Exact-key decoding rejects unknown and missing fields at the
request, signal, source, instrument, and target levels.

Direct constructors retain typed exact `Decimal` and canonical UTC `datetime`
values. Dictionary codecs accept only strict strings and produce the same
semantic requests. `to_dict()` always emits normalized JSON-safe values.

## Syntax and Limits

Source ID/version/event ID, symbol, venue, and timeframe are visible ASCII only,
contain no whitespace, and are limited respectively to 128, 64, 256, 64, 32,
and 32 characters. Configuration fingerprints use the repository SHA-256
format.

Decimal text matches `[0-9]+(?:\.[0-9]+)?`, is limited to 256 characters, 128
total digits, and 64 fractional digits, and never passes through float. Leading
and trailing zeros normalize (`0001.2500` becomes `1.25`). Signs, negative zero,
exponents, whitespace, separators, NaN, and infinity are rejected. Direct typed
Decimals are projected from tuple state before fixed-point formatting, so
pathological positive or negative exponents are rejected without exponent-sized
allocation. Positive zero is canonicalized before sizing; signed zero is rejected.

Timestamps are at most 64 characters and require the strict
`YYYY-MM-DDTHH:MM:SS[.ffffff](Z|±HH:MM)` form with one-to-six fractional digits.
Offset hours are 00–23 and minutes are 00–59. `Z` and `+00:00` declare UTC;
`-00:00` is rejected because it denotes an unknown offset. Accepted timestamps
normalize to UTC `+00:00`; equal instants with different accepted offsets have
equal request identity.

## Identity and Correspondence

The signal-request fingerprint covers its schema and complete normalized signal
input. The intent-request fingerprint additionally covers canonical
`decision_as_of` and the fixed exact-target policy fingerprint. Limits, raw
syntax, receipt/authentication data, current time, account state, risk, and
broker state are excluded.

The signal response validates every source, event, instrument, target, time,
idempotency, and signal identity. The intent response additionally validates the
retained source signal, fixed policy, decision and validity times, target, and
intent fingerprint. Quantity correspondence requires exact canonical Decimal
tuple and fixed-point state; numeric equality or fingerprint equality alone is
insufficient. An unrelated request/domain pairing or fabricated derived identity
raises `TradingApplicationCorrespondenceError`.

## Service and Response Semantics

`CreateTradingSignalApplicationService.execute()` constructs exactly one signal
and stops. `CreateOrderIntentApplicationService.execute()` reconstructs exactly
one signal, creates one fixed policy, invokes the released intent conversion
once, and preserves not-yet-valid and expired domain errors.

Responses retain the complete signal or intent while dictionaries embed only
the bounded released domain projections plus the application request
fingerprint. They contain no raw request, runtime object, Decimal, datetime,
enum, exception text, credential, path, or response fingerprint.

## Trust and Idempotency Boundaries

This is a trusted-local boundary. Source acceptance is not authentication, and
instrument acceptance is not existence, tradability, account permission, or
broker mapping. Idempotency keys identify logical events; no idempotent
processing, storage, deduplication, conflict quarantine, queue, or retry state is
implemented.

## Scope and Compatibility

There is no TradingView/HTTP schema or server, authentication, ingress receipt,
persistence, account/position/market state, risk decision, execution planning,
broker adapter/order, live trading, CLI, Agent, UI, provider, filesystem, or
network behavior. Existing v0.54 application and v0.55 domain public APIs and
fingerprints remain unchanged.
