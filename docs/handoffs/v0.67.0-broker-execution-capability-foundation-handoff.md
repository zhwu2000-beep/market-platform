## Capability profile

The keyword-only profile factory requires opaque execution-target identity,
nonempty exact tuples of asset classes, currencies, venues, and exact
style/TIF/session combinations. It performs no collection coercion or sorting.
Duplicates, noncanonical ordering, raw strings replacing enums, string
subclasses, and values outside the schema-frozen v1 maps fail.

Target IDs match exact ASCII
`[A-Za-z0-9][A-Za-z0-9._-]{0,127}`. Trading currencies reproduce the
canonical-instrument exact uppercase ASCII `[A-Z]{3}` rule. Venues reproduce the
state retainable by the current `TradingInstrumentIdentity` and
`CanonicalInstrument` boundary: exact built-in, nonempty, already-trimmed
uppercase strings without whitespace. Permanent accepted/rejected parity cases
exercise both boundaries without claiming exhaustive proof.

Asset ranks are `EQUITY`, `ETF`; style ranks are MARKET, LIMIT; TIF ranks are
DAY, GTC, IOC, FOK; session ranks are regular-only, then regular-and-extended.
Combination ordering uses those three ranks in order. Asset and combination
maximums derive from the frozen maps; all 16 current combinations are accepted
when supplied canonically. Currency and venue collections have no arbitrary
configured count limit.

## Structural compatibility

The evaluator independently validates the complete v0.66 specification and the
profile. It evaluates asset class, trading currency, venue, style, TIF, session,
and exact combination in that fixed order. Individual style/TIF/session support
is derived from declared combinations. The combination reason appears only when
all three components are individually supported but the exact triple is absent.

Asset, currency, and venue support are intentionally independent domains in v1.
The model has no asset/venue, currency/venue, asset/currency/venue,
product-specific, or venue-policy matrix. LIMIT price value is outside the
capability algorithm after the source specification proves its own validity.

Compatible results require exact retained `()` and project `[]`. Incompatible
results require at least one unique exact reason in schema-frozen canonical
order. Normal incompatibility is a result, not an exception. Structural
compatibility covers only declared dimensions and is not a promise of broker
acceptance or complete executability.

## Value-semantic correspondence boundary

The profile and result are self-contained frozen/slotted canonical value
artifacts. They validate exact current field types, tuple and ordering rules,
schema, outcome/reason invariants, and recomputed fingerprint. The result
retains only validated source fingerprint strings; it contains no source
objects, source projections, registry, attestation, weak reference, owner
identity, or process-local authority.

A coherent low-level rewrite of every semantic field and fingerprint into
another valid canonical value is outside construction-origin authenticity.
Fingerprints provide deterministic identity and provenance binding, not
cryptographic authenticity or immutable original-factory provenance. Malformed
or incoherent retained state is rejected, but v0.66's external origin registry
is deliberately not copied.

## Projection and errors

Profile projection keys are schema, target ID, asset classes, currencies,
venues, order combinations, and fingerprint. Combination objects project exact
`order_style`, `time_in_force`, and `session_participation` keys. Result
projection keys are schema, profile fingerprint, specification fingerprint,
outcome, rejection reasons, and fingerprint. Tuples project as JSON lists.
Fingerprint payloads use the same ordered JSON-safe values and omit only the
fingerprint.

Malformed public factory inputs raise `ExecutionPlanningValidationError`.
Malformed retained state and corrupted sources encountered during evaluation
raise `ExecutionPlanningCorrespondenceError`. Direct construction raises
`TypeError`. Unrelated controlled exceptions are not broadly masked.

## Scope

There is no broker SDK, credential, account, balance, buying power, live market
state, calendar, current-time query, capability discovery, network access,
retry, persistence, configuration or environment loading, broker-native
mapping, native payload, routing, submission, cancellation, replacement,
acknowledgement, lifecycle, fill, commission, rate limit, authorization, risk
approval, quantity bound, fractional-share capability, lot, tick, collar,
price-band, product rule, account rule, or cross-dimensional instrument matrix.

The next recommended milestone is a pure-domain Broker-Native Order Mapping
Foundation. Authorization remains later and must bind specification,
compatibility, structural-risk evidence, and explicit authorization policy
identity rather than wrapping compatibility alone.

## Final-review corrections

The three required final-review findings are resolved without production
semantic redesign. The asset v1 rank regression now compares the frozen map
with the current InstrumentAssetClass inventory, so enum/schema divergence
requires explicit review. Permanent compatibility regressions now reject exact
source subclasses, reason string subclasses, and equality-spoof values before
comparison, and prove that outcome/reason contradictions remain invalid after
the top-level result fingerprint is recomputed. Public profile, result, and
evaluator documentation now states the bounded independent structural scope
and explicitly denies complete broker executability.
