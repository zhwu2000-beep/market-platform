# v0.48.0 Replay Specification and Context Window Handoff

## Release Status

Implementation is complete and validated on
`feature/v0.48.0-replay-specification-context-window`, but remains intentionally
uncommitted and unreleased. No merge, tag, push, or package-version change has
been performed. Package version remains `0.1.0`.

## Scope

v0.48.0 separates historical analytical context from the inclusive replay
evaluation window while preserving released defaults and result schemas:

- introduce immutable `HistoricalReplaySpecification`;
- retain context rows for signal and structure precomputation;
- create replay steps only inside the evaluation window;
- add optional CLI `--context-start`, defaulting to `--start`;
- apply `--max-bars` to evaluation rows rather than context rows;
- preserve legacy `HistoricalReplayService.run()` behavior.

## Temporal Semantics

- `context_start <= evaluation_start <= evaluation_end`.
- Specification timestamps must be aware and are normalized to UTC.
- Context is retained inclusively from `context_start` through `evaluation_end`.
- Evaluation positions are inclusive from `evaluation_start` through
  `evaluation_end`.
- A requested boundary is not a coverage assertion and need not have an exact bar.
- Zero returned pre-evaluation rows is valid when evaluation rows exist.
- Each replay observation is evaluated at its selected canonical prefix endpoint.
- CLI dates map to UTC day start for context/evaluation starts and UTC day end for
  evaluation end. Provider fetch end remains the following calendar date.

See `docs/adr/0005-replay-specification-context-window.md`.

## Compatibility Guarantees

- CLI `--start` and `--end` remain inclusive evaluation dates.
- Omitting `--context-start` preserves the v0.47.0 acquisition start and replay
  result for equivalent provider data.
- Legacy direct service callers retain the complete supplied DataFrame as
  analytical context; optional `start`/`end` still select steps without discarding
  earlier rows.
- Canonical historical validation, future-data isolation, default structure
  precompute, custom structure-service prefix copies, observation identity, state
  and strategy identity propagation remain intact.
- `HistoricalReplayResult.to_dict()`, step, summary, table, JSON, and CSV schemas
  are unchanged.
- Existing 100/300/500-bar benchmark fingerprints remain unchanged.

## Current Limitations

- `context_start` expresses requested/allowed history, not guaranteed provider
  coverage or a component-sufficient warm-up.
- No exchange calendar resolves preceding sessions or missing bars.
- Current analytical components do not expose a common historical-requirement
  contract.
- Context and actual dataset coverage are not included in result serialization.
- Fingerprint row traversal remains cumulative and is unchanged.

## Explicit Non-Goals

Warm-up bars or duration, component-derived lookback, resolved execution plans,
run manifests, result metadata, persistence, cache integration, dataset registries,
exchange calendars, security master, intraday semantics, provider-lineage redesign,
research migration, portfolio/risk/execution/accounting domains, fingerprint
optimization, workflow engines, event buses, microservices, and package-version
changes.
