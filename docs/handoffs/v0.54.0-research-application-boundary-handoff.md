# v0.54.0 Research Application Boundary Foundation Handoff

## Release Status

Implementation is complete on
`feature/v0.54.0-research-application-boundary`, remains uncommitted, and is
unreleased. Package version remains `0.1.0`.

## Schemas and Public Boundary

- request: `historical_replay_research_application_request/v1`;
- response: `historical_replay_research_application_response/v1`.

`market_platform.application` exports immutable request/source/row/member/
strategy/state models, a factory-only response, the synchronous service,
strategy/state resolver protocols, built-in resolvers, the strict decoder,
schema constants, and narrow exceptions.

The request owns inline symbol/interval/provider and strictly ordered UTC OHLCV
rows; an exact five-field Replay specification per member; ordered strategy
requests; state-model request; complete structure identity; ordered candidates;
and explicit Replay, comparison, and workflow revisions. It retains no
DataFrame, domain source, executable, service, callable, path, URL, or secret.

## Identity and Resolution

The request fingerprint covers normalized rows and derived row count, every
member/configuration, indexed candidates, structure identities, and all three
revisions including dirty flags. Mapping order is neutral; row, strategy, and
candidate order are significant.

Public constructors and the strict codec share one recursively enforced
passive-JSON contract. Nested mappings are immutable, sequences are ordered
tuples, and sets, runtime objects, and non-finite floats are rejected. Integer
values remain exact integers and floats remain floats: request identity
distinguishes `1` from `1.0`, `0.0` from `-0.0`, and preserves integers larger
than the IEEE-754 exact range. Some externally distinct numeric requests may
deliberately resolve to equal canonical workflow intent.

Application request, resolved workflow specification, and workflow result have
distinct fingerprints. No response fingerprint exists.

Built-in immutable allow lists expose:

- `BaselineTrendRegimeStrategy`;
- `BaselineVolatilityRegimeStrategy`;
- `BaselineMarketStateModel`.

Factories create fresh instances. The service rechecks exact runtime ID,
version, and configuration fingerprint. The baseline state model accepts empty
configuration and a null expected fingerprint only. Dynamic imports, shared
mutable instances, and global registries are absent.

Allow-listed configuration validators translate only expected configuration
failures into dedicated resolution errors. Factory construction occurs outside
that boundary, so unexpected factory `TypeError`, `ValueError`, and other
programming defects propagate unchanged.

## Service, Errors, and Response

`HistoricalReplayResearchApplicationService.execute()` creates the canonical
`HistoricalPriceSeries`, resolves members, constructs the exact v0.53 workflow
specification, invokes `HistoricalReplayResearchWorkflowService.run()` once,
and returns a response retaining that complete workflow result.

Response construction proves the exact executed specification/result binding
and compares the full request-derived semantic projection with the resolved
source, Replay windows, ordered members, strategy/state identities, structure
identities, fixed v0.53 policy, and revisions. A request cannot be paired with
an unrelated workflow result. Each response retains its own application
request fingerprint even when distinct external requests resolve to equal
workflow intent.

The response dictionary is JSON-safe and bounded to schema, fingerprint
hierarchy, workflow status, canonical steps, baseline/candidate identities and
terminal codes, and optional Experiment compatibility/comparison identities.
It excludes source rows, Replay steps, Artifact bodies/checksums/bytes,
DataFrames, executables, exception messages, paths, and tracebacks.
Large source, member, candidate, and configuration fields are also excluded
from dataclass representations so ordinary logging remains bounded.

Codec/schema, source validation, strategy resolution, state resolution, and
resolver identity mismatch use dedicated exceptions. Source `TypeError` and
`ValueError` are translated only around `HistoricalPriceSeries` construction.
Workflow outcomes and defects retain v0.53 behavior and are not broadly caught.

## TradingView Future Boundary

The approved direction is a separate future TradingView Signal Gateway and
Trading Signal application operation, followed by explicit Order Intent, Risk,
and Paper/Broker Execution layers. A TradingView alert is not this historical
request. Future ingress requires HTTPS, authentication, bounds, fast
acknowledgement, idempotency, durable receipt, expiry/replay protection, and
symbol/timeframe mapping. Alert payloads contain no passwords or broker
credentials; browser automation is rejected.

## Recommended Next Direction

A tentative next investigation is **v0.55.0 Trading Signal and Order Intent
Foundation**. It must separately approve signal, risk, authorization, and
idempotency semantics before any TradingView webhook implementation is accepted.
