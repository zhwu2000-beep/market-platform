## 2. Milestone boundary

The delivered governed flow is:

```text
authenticated governed Assessment occurrence
→ exact bound Interpretation
→ deterministic descriptive Strategy
→ Strategy publication/history
→ STOP
```

Strategy remains descriptive research authority. v0.82 stops before thesis
approval, recommendation, buy point, target, stop, sizing, signal, order intent,
risk approval, execution planning, execution authorization, and Agent/trading
automation. There are no action-bearing output fields or downstream integrations.

- `no_active_strategy` is NOT hold, flat, exit or avoid.
- `positive_directional_continuation` is NOT buy or long.
- `negative_directional_continuation` is NOT sell or short.

## 6. Refusal contract

`PolygonCompletedDailyStrategyRefused` exposes exact built-in reason strings
through `PolygonCompletedDailyStrategyRefusalReason`:

| Constant | Frozen reason |
| --- | --- |
| `ASSESSMENT_UNAVAILABLE` | `assessment_occurrence_unavailable` |
| `HISTORY_INVALID` | `history_incomplete_or_corrupt` |
| `SOURCE_MISMATCH` | `source_lineage_mismatch` |
| `SEMANTIC_FAILED` | `semantic_execution_or_correspondence_failed` |
| `TEMPORAL_FAILURE` | `temporal_failure` |
| `PUBLICATION_FAILED` | `strategy_publication_or_copy_failed` |

Missing/lost committed support and invalid committed Assessment/Strategy semantics
are `HISTORY_INVALID`. Authenticated lineage or selector correspondence mismatch
is `SOURCE_MISMATCH`. An exact new requested Assessment absent from valid complete
history, or unavailable by execution start, is `ASSESSMENT_UNAVAILABLE`.
Candidate Strategy semantic invalidity is `SEMANTIC_FAILED`; invalid new temporal
values/order are `TEMPORAL_FAILURE`; staging/copy/publication preparation failures
are `PUBLICATION_FAILED`.

Complete committed support invalidity takes precedence over new-selector absence.
Classification uses structured failure categories and operation stages, with no
diagnostic-string parsing. Authentication failure never becomes a descriptive
fallback mode.

## 7. Authority, transactions and atomicity

The exact eleven-lock order is:

```text
Construction → Validation → Freshness → Admission → Validity
→ Qualification → Bridge → Technical → Interpretation → Assessment → Strategy
```

The existing upstream chain is acquired once through the pinned Assessment
publisher, with the original Strategy owner eleventh/final. There is no recursive
acquisition or public upstream execute/history call under those locks.

- Authenticate the complete Assessment inventory before selection and the
  complete Interpretation inventory, including unrelated, unselected and
  invisible entries, even when downstream selection is empty.
- Resolve only the exact bound Interpretation and its original Technical
  occurrence/issuance, with complete original upstream lifecycle, governance,
  mapping, material, Bridge and historical support.
- Keep prepared data transaction-local, non-authoritative and separate from
  original authority anchors. Possession, copying or prior success grants no
  bearer authority or cross-call trust.
- Use an explicit Strategy-created transaction ownership witness, owner-thread
  enforcement, a non-reentrant lifecycle, failure invalidation and closure before
  releasing locks.
- Complete fallible preparation and canonical rechecks across the entire
  inventory before final complete original-support continuity checks. Preserve
  only direct authority/identity/scalar checks, original-owner pending cleanup,
  preallocated state advancement and return after the seal.
- Commit complete canonical immutable bytes. Failed publication appends nothing,
  preserves prior commitments, clears original pending state and leaves the
  sequence reusable. Readers observe complete old or new state; history is
  read-only with respect to authority.

Source authentication performs no provider/source refetch, upstream lifecycle
execution, technical analysis, or Interpretation semantic rerun. Independent
Assessment/Strategy semantic validation remains a separate required stage.
Drift causes refusal without repair, adoption, fallback or reissuance.

## 8. Historical storage continuity

ADR0045 is implemented as private continuity capture/compare in
`src/market_platform/data/historical.py`. It supports the exact audited pandas
storage representation: the reviewed pandas 3.0.3 / NumPy 2.5.0 layout with
`BlockManager`, approved numeric/datetime/string blocks, Python-backed strings,
UTC nanosecond timestamps and native `float64` values. These versions describe
the audit environment, not a new dependency pin or universal backend guarantee.

The final callback-free comparison reads current live frame/manager/block/backing
attachments and checks exact content, index, dtype and column order against the
original expectation. It includes stored `_blknos` / `_blklocs` routing values,
attachment and absent/materialized continuity, plus stored logical dtype-cache
continuity. Unsupported storage fails closed before untrusted dispatch.

The comparison follows all mutation-capable support work; it cannot recapture,
normalize or repair drift. Public `HistoricalPriceSeries` API and fingerprint
semantics remain unchanged. The private expectation is neither a new public
fingerprint nor a persistent authentication certificate.

## 11. Post-release test-runtime observation

Full-suite runtime remains approximately **3.5 hours**, and several authentic-chain
tests individually take multiple minutes. The earlier pathological behavior of
requiring more than ten hours to reach approximately 66% of the suite was traced
to repeated complete authentication and materially corrected. Remaining runtime
now appears substantially related to expensive authentic integration/authority
tests and their setup; this is an engineering observation, not an unresolved
v0.82 correctness defect or a completed attribution of every slow test.

The next architecture/roadmap review should explicitly consider:

- Test-runtime architecture and unit versus authentic/integration versus
  release-only test layering.
- Profiling the slowest tests and safe fixture reuse.
- Sharding/parallelism where lock and concurrency semantics allow it.
- Avoiding repeated full-suite execution during ordinary slice development.

These are review recommendations, not an approved implementation plan.
