## Architecture and layer semantics

The released application pipeline is:

```text
DailyTechnicalStrategyApplicationRequest
    -> IntegrityCheckedDailyTechnicalResearchResult
    -> DailyTechnicalInterpretation
    -> DailyTechnicalAssessment
    -> DailyTechnicalStrategy
    -> DailyTechnicalStrategyApplicationResponse
```

`market_platform.application` owns transport-neutral orchestration and
application correspondence. The released research domain runners and policies
remain the sole authorities for Interpretation, Assessment, and Strategy
semantics.

The service starts from a completed verified research result. It does not own
market-data acquisition, instrument verification, presentation, persistence,
or transport behavior.

## Request contract

`DailyTechnicalStrategyApplicationRequest` is frozen and slotted. It retains
exactly:

- an exact `IntegrityCheckedDailyTechnicalResearchResult` as
  `verified_research`;
- fixed schema version
  `daily_technical_strategy_application_request/v1`; and
- a computed `request_fingerprint`.

The fingerprint is computed from the fixed request schema and the complete
canonical verified-research projection. Callers cannot provide it. It binds
the normalized request to the v0.75 fixed application profile, but it is not a
domain fingerprint or proof of authorship.

Raw daily research, `DailyTechnicalResearchResult`, historical
`ResearchResult`, subclasses, and reconstructed substitutes are not accepted.
Nested source integrity and stale or forged fingerprints fail closed.

## Fixed application profile

`DailyTechnicalStrategyApplicationService` receives the three domain policies
through dependency injection but accepts only implementations exposing the
complete released Classic identities:

- Interpretation: `classic_daily_technical@1.0.0`;
- Assessment: `classic_daily_technical_coherence@1.0.0`; and
- Strategy: `classic_daily_technical_strategy@1.0.0`.

Each identity includes its exact kind, policy ID, behavioral revision, typed
configuration, configuration schema, and fingerprint. The service validates
all three identities before invoking any runner. Dependency injection permits
an implementation replacement with the same released semantics; it is not a
caller-selectable policy registry.

## Orchestration guarantees

For each successful call, the service:

1. validates the exact request and its retained integrity;
2. captures and validates all three policy identities;
3. invokes the released Interpretation runner once;
4. invokes the released Assessment runner once with that Interpretation;
5. invokes the released Strategy runner once with that Interpretation and
   Assessment; and
6. constructs one correspondence-validated response.

The ordered stages are intentionally not concurrent. The async service
preserves the established application workflow seam for future composition; it
does not imply application-owned I/O.

The application layer does not recompute comparison evidence, states,
assessment findings or outcome, Strategy mode, or Strategy rule code. It also
does not import private domain semantic helpers.

## Response contract

`DailyTechnicalStrategyApplicationResponse` is factory-created, frozen, and
slotted. It retains exactly:

- `application_request_fingerprint`;
- the complete `DailyTechnicalInterpretation` object;
- the complete `DailyTechnicalAssessment` object;
- the complete `DailyTechnicalStrategy` object; and
- fixed schema version
  `daily_technical_strategy_application_response/v1`.

The response has no response, aggregate, or pipeline fingerprint. v0.75 adds
only the request fingerprint family.

Response construction validates the complete domain chain against the request:
instrument identity, requested trading identity, analysis time, source
fingerprints, source quality and warnings, policy identities, and the released
Interpretation -> Assessment -> Strategy lineage must correspond. Canonically
equivalent independently reconstructed domain objects are accepted; object
identity is not required.

## Failure semantics

The boundary is success-only. Invalid request state, policy-profile mismatch,
domain-stage failure, or response-correspondence failure produces no response.

The exact original domain-stage exception propagates. There is no retry,
fallback, alternate policy, partial response, or rollback promise. Later stages
are not invoked after an earlier failure.

## Parallel ontology and legacy separation

The existing `research-workflow-v1` ontology remains parallel and untouched.
`DefaultResearchWorkflow`, the `research run` command, and `ResearchResult` are
not inputs, adapters, migration surfaces, or compatibility targets for this
boundary.

The legacy `market_platform.strategy.Strategy` family also remains separate.
The application service does not populate or consume
`ResearchResult.strategy_candidates` or `ResearchResult.position_actions`.

Do not introduce a conversion between either parallel family and the daily
technical application contract without an explicit future architecture
decision.

## Semantic and implementation non-goals

The returned `DailyTechnicalStrategy` remains descriptive. In particular:

- `NO_ACTIVE_STRATEGY` is not HOLD, EXIT, CLOSE, or STAY FLAT;
- positive directional continuation is not BUY, LONG, or OPEN LONG; and
- negative directional continuation is not SELL, SHORT, or EXIT LONG.

v0.75 adds no CLI command, rendering, JSON/dictionary codec, HTTP API, Agent
tool, provider acquisition, persistence, cache, queue, retry, fallback,
rollback, Trade Planning, position sizing, risk decision, execution
authorization, broker mapping, order submission, TradingView integration, or
AI recommendation.

Any future CLI or transport for this use case must invoke
`DailyTechnicalStrategyApplicationService`. It may own input decoding,
presentation, and transport-specific error mapping, but it must not reproduce
the three-stage domain orchestration.

## Market Intelligence Agent ADR status

ADR 0033 is present in the release tree with status `Proposed`. It is design
guidance for possible future Agent exposure and introduces no code or behavior.
Do not treat its presence as approval to implement an Agent, expose the generic
application package, or connect intelligence output to Trade Planning, Risk,
Execution, or broker activity.

Its central constraint is:

```text
Agent
    -> explicit Agent exposure adapter/facade
        -> allow-listed application capabilities
            -> application services
                -> domain boundaries
```

An Agent remains an external consumer. Financial semantics remain platform
owned and deterministic; prompt text, model reasoning, memory, presentation,
and tool descriptions are not policy implementations or authoritative inputs.

## Recommended next architectural starting point

Treat the released v0.75 application boundary and the v0.74 domain contracts
as frozen unless a real defect is discovered.

Before implementing Agent or other external exposure, first decide whether to
accept, revise, or reject ADR 0033. If external exposure is approved, design a
narrow, versioned, bounded transport projection for one explicitly allow-listed
application capability. That projection must delegate to
`DailyTechnicalStrategyApplicationService` and preserve lineage without
serializing the complete in-memory graph automatically.

Do not begin Trade Planning, Risk, Execution, broker integration, TradingView
ingress, or a generic Agent executor automatically. Each requires its own
explicit contract, authority boundary, and scope approval.

### First reconnaissance questions

Ask these questions before proposing the next implementation:

1. Is ADR 0033 accepted as the governing direction, or should it be revised?
2. Which single application capability, if any, should be exposed first?
3. Which consumer is in scope: Agent, CLI, HTTP API, UI, or another adapter?
4. What bounded request and response projection should that consumer receive?
5. Which provenance, policy identity, and timestamp fields must remain visible?
6. What authentication, authorization, resource-limit, and error-mapping rules
   belong to the selected transport?
7. How will the exposure remain allow-listed and read-only with respect to
   Trade Planning, Risk, Execution, and broker activity?
