# v0.78.0 Polygon Daily Evidence Ingress handoff

## Release status

### Released fact

v0.78.0 was released locally from `main` through a reviewed non-fast-forward
merge and an annotated release tag. It establishes the first and only
production-authorized Evidence ingress at this release: the exact governed
Massive.com, formerly Polygon.io, completed-daily Stocks Custom Bars profile.

The release constructs immutable, unvalidated, unadmitted `EvidenceArtifact`
Candidates for read-only inspection. Production authorization permits the
governed contract, source, and type to construct a Candidate; it is not a
claim about the truth, accuracy, validity, freshness, completeness, admission,
consumability, or research suitability of any particular Candidate.

### Future roadmap / not yet implemented

Evidence validation, admission, and downstream Daily Technical consumption
remain future work. Nothing in this release or handoff implements or
pre-approves that work.

## Implementation structure

The implementation preserves narrow boundaries:

- the HTTP boundary preserves JSON numeric values exactly for provider
  decoding;
- the Polygon provider retains exact request, response, row, pagination, and
  receipt facts in an immutable completed-daily acquisition record;
- the private Evidence authorization boundary contains the single exact
  production catalog member and the contract-specific artifact constructor;
- the pure `evidence_ingress` boundary enforces source-profile and response
  correspondence, resolves the trusted canonical instrument mapping,
  canonicalizes completed-day material, derives temporal/provenance and
  artifact identities, and constructs the Candidate;
- the application service receives the acquirer and creation clock through
  dependency injection, performs mapping preflight, and composes acquisition
  with pure ingress; and
- the CLI loads an explicit operator mapping and presents the Candidate for
  read-only inspection. Live provider smoke remains explicit opt-in.

Acquisition, material construction, production authorization, lifecycle
validation, admission, and downstream consumption remain distinct concerns.

## Candidate boundary

At v0.78 release, the exact lifecycle posture is:

```text
lifecycle_state: candidate
semantic_authorization: exact_production_membership
validation: not_performed
admission: absent
validity: not_evaluated
freshness: not_evaluated
consumable: false
research_permitted: false
```

> UNVALIDATED, UNADMITTED CANDIDATE — NOT PERMITTED FOR RESEARCH

Production authorization means the Evidence contract, source, and type are
permitted to construct a governed Candidate. It does not mean the specific
Candidate is validated, admitted, fresh, valid, complete, accurate,
consumable, or suitable for research.

## What v0.78 does not implement

v0.78 does not implement:

- Evidence validation execution;
- validation records;
- Evidence admission;
- validity activation;
- freshness evaluation;
- final consumability;
- a `CompletedDailyPriceSeries` bridge;
- Daily Technical Evidence consumption;
- research consumption;
- specialist or Agent exposure of this Evidence;
- persistence or replay of admitted Evidence;
- generic multi-source Evidence ingress; or
- automatic trading or execution.

None of these capabilities should be inferred from Candidate construction or
inspection.

## Starting point for v0.79

### Future roadmap / not yet implemented

The expected next release direction is Evidence validation and admission,
followed by a bridge from admitted completed-daily Evidence into Daily
Technical consumption. This is roadmap context only; this handoff neither
designs nor implements v0.79.

Any v0.79 work must preserve:

- Evidence Candidate immutability;
- source, material, and provenance identity;
- validation as distinct from Evidence construction;
- admission as distinct from validation;
- final consumability derived through the existing Evidence lifecycle; and
- no direct Candidate-to-research bypass.

Whether v0.79 requires an ADR is deferred to the next architecture checkpoint.
