## Architecture and layer semantics

The released domain pipeline is:

```text
IntegrityCheckedDailyTechnicalResearchResult
    -> DailyTechnicalInterpretationPolicy
    -> DailyTechnicalInterpretation
    -> DailyTechnicalAssessmentPolicy
    -> DailyTechnicalAssessment
    -> DailyTechnicalStrategyPolicy
    -> DailyTechnicalStrategy
```

- Interpretation answers: "What market state exists?"
- Assessment answers: "How coherent, conflicting, incomplete, or cautionary is
  that state?"
- Strategy answers: "What strategy logic is applicable to the interpreted and
  assessed state?"
- Trade Planning is a future, separate layer that may translate Strategy
  semantics into concrete trade parameters or actions.

v0.74 intentionally stops at Strategy.

## Strategy value contract

`DailyTechnicalStrategy` uses the fixed schema
`daily_technical_strategy/v1` and retains:

- `canonical_instrument_id`
- `analysis_as_of`
- `source_assessment_fingerprint`
- `strategy_policy_identity`
- `mode`
- `rule_code`
- fixed `schema_version`
- computed `fingerprint`

Strategy stores only the immediate Assessment fingerprint. Assessment already
binds Interpretation, and Interpretation transitively binds the verified
technical-research lineage. Do not add a duplicate
`source_interpretation_fingerprint` without an explicit future contract change.

## Frozen Classic mapping

| Assessment/state | Strategy mode | Rule code |
| --- | --- | --- |
| `INSUFFICIENT_DATA` | `NO_ACTIVE_STRATEGY` | `INSUFFICIENT_DATA_NO_ACTIVE_STRATEGY` |
| `MIXED` | `NO_ACTIVE_STRATEGY` | `MIXED_NO_ACTIVE_STRATEGY` |
| `CAUTION` | `NO_ACTIVE_STRATEGY` | `CAUTION_NO_ACTIVE_STRATEGY` |
| `ALIGNED` + trend `POSITIVE` + momentum `POSITIVE` | `POSITIVE_DIRECTIONAL_CONTINUATION` | `ALIGNED_POSITIVE_CONTINUATION` |
| `ALIGNED` + trend `NEGATIVE` + momentum `NEGATIVE` | `NEGATIVE_DIRECTIONAL_CONTINUATION` | `ALIGNED_NEGATIVE_CONTINUATION` |

Frozen v0.73 semantics establish that valid `ALIGNED` directional states are
exactly positive/positive or negative/negative, with no caution finding.
Unsupported `ALIGNED` states and unsupported future Assessment outcomes fail
closed.

## Semantic authority and integrity guarantees

`ClassicDailyTechnicalStrategyPolicy` owns the Classic Strategy mapping.
`derive_daily_technical_strategy()` owns:

- exact source validation;
- Interpretation/Assessment coherence;
- Assessment semantic reconstruction;
- pre/post detached source integrity;
- Strategy policy identity validation and policy identity drift defense;
- the single invocation boundary;
- Strategy result/source correspondence; and
- Strategy result/policy correspondence.

The runner intentionally does not recompute the Classic Strategy mode/rule
mapping. Keep this authority separation explicit.

The boundary has adversarial coverage for source mismatch, lineage
substitution, forged Assessment findings/outcomes, nested Assessment mutation,
coherent re-fingerprinting, policy identity replacement, policy revision or
configuration-family drift, wrong-source or wrong-policy Strategy results,
stale Strategy fingerprints, and exact-type/subclass boundaries.

Canonical semantic equality is authoritative: separate Python objects with
identical canonical semantics are accepted. Exact temporary semantic mutation
followed by restoration before a successful return is also accepted.

If a Strategy policy raises, the exact original exception instance propagates.
There is no retry or fallback, no Strategy is returned, no transactional
rollback is promised, and external mutation may remain. Fingerprints are
deterministic semantic-integrity checks, not cryptographic proof of authorship
or constructor provenance.

## Semantic and implementation non-goals

`NO_ACTIVE_STRATEGY` does not mean HOLD, EXIT, CLOSE, STAY FLAT, retain a
position, portfolio behavior, or execution behavior.

`POSITIVE_DIRECTIONAL_CONTINUATION` does not mean BUY, LONG, OPEN LONG, or ADD.
`NEGATIVE_DIRECTIONAL_CONTINUATION` does not mean SELL, SHORT, EXIT LONG, or
OPEN SHORT. These values are descriptive Strategy semantics only.

v0.74 does not implement broker integration, automated trading, orders, order
intent, `TradingSignal` integration, position sizing, portfolio or risk
allocation, entry price, stop loss, target price, quantity, execution side,
TradingView webhooks, AI recommendations, Strategy CLI/application wiring,
legacy `market_platform.strategy` integration,
`ResearchResult.strategy_candidates` integration,
`ResearchResult.position_actions` integration, or Trade Planning.

## Current application-wiring status

v0.74 is domain-only.

The existing `market-platform research analyze` application boundary returns
daily technical research. The existing `market-platform research
analyze-verified` application boundary returns integrity-checked daily technical
research. Neither boundary automatically invokes or composes:

- `DailyTechnicalInterpretation`
- `DailyTechnicalAssessment`
- `DailyTechnicalStrategy`

The existing `market-platform research run` command remains on the older,
parallel `research-workflow-v1` stack. It does not automatically execute the
v0.73/v0.74 Interpretation -> Assessment -> Strategy domain pipeline.

Strategy Foundation is not user-facing yet.

## Recommended next architectural starting point

Treat the released Strategy Foundation as frozen unless a real defect is
discovered. The next likely phase is a narrow application/composition boundary
that composes the released domain layers into a usable higher-level workflow:

```text
verified daily technical research
    -> Interpretation
    -> Assessment
    -> Strategy
```

Determine how this boundary should coexist with `research-workflow-v1` without
prematurely merging their ontologies. The first boundary may remain
library-only or expose a narrow CLI surface, but that choice requires explicit
design approval.

Do not begin Trade Planning automatically. Trade Planning remains separate and
must not be pulled into the first application-boundary implementation unless it
is explicitly approved later.
